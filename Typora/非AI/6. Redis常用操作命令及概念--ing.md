## Redis 常用操作命令及概念

### 一、Redis 服务端和客户端操作命令

#### 1.1 启动服务端

```
redis-server
# 前台启动

redis-server &
# 后台启动

redis-server redis.conf &
# 带配置文件后台启动
# 如果修改了redis的配置文件redis.conf，必须在启动时指定配置文件，否则修改无效！
```

#### 1.2 关闭服务端

```
redis-cli shutdown
# redis先完成数据操作，再关闭

ps -ef | grep redis
kill -9 xxxx
# 使用Linux的kill命令关闭
```

#### 1.3 启动客户端

- redis-cli（Redis Command Line Interface）是Redis自带的基于命令行的Redis客户端

```
redis-cli -h 192.xxx.xxx.xx -p 6379
```

#### 1.4 退出客户端

```
exit 或者 quit
```

### 四、Redis 的配置文件

#### 4.1 redis.conf存放位置

1、 Redis的安装根目录下(/opt/redis-5.0.2)，Redis在启动时会加载这个配置文件，在运行时按照配置进行工作。 这个文件有时候我们会拿出来，单独存放在某一个位置，启动的时候必须明确指定使用哪个配置文件，此文件才会生效。



#### 4.2 Redis的网络相关配置

1、 `bind`：绑定IP地址，其它机器可以通过此IP访问Redis，默认绑定127.0.0.1，也可以修改为本机的IP地址。

2、`port`：配置Redis占用的端口，默认是6379。

3、`tcp-keepalive`：TCP连接保活策略，可以通过tcp-keepalive配置项来进行设置，单位为秒，假如设置为60秒，则server端会每60秒向连接空闲的客户端发起一次ACK请求，以检查客户端是否已经挂掉，对于无响应的客户端则会关闭其连接。如果设置为0，则不会进行保活检测。



#### 4.3 Redis的常规配置

1、loglevel：日志级别，开发阶段可以设置成debug，生产阶段通常设置为notice或者warning.

2、logfile：指定日志文件名，如果不指定，Redis只进行标准输出。要保证日志文件所在的目录必须存在，文件可以不存在。还要在redis启动时指定所使用的配置文件，否则配置不起作用。

3、databases：配置Redis数据库的个数，默认是16个。



#### 4.4 Redis的安全配置

1、requirepass：配置Redis的访问密码。默认不配置密码，即访问不需要密码验证。此配置项需要在protected-mode=yes时起作用。使用密码登录客户端：redis-cli -h ip -p 6379 -a pwd



#### 4.5 Redis的RDB配置

1、`save <seconds> <changes>`：配置复合的快照触发条件，即**Redis 在seconds秒内key改变changes**次，Redis把快照内的数据保存到磁盘中一次。默认的策略是：

​	1分钟内改变了1万次

​	或者5分钟内改变了10次

​	或者15分钟内改变了1次

如果要禁用Redis的持久化功能，则把所有的save配置都注释掉。

2、**stop-writes-on-bgsave-error：**当bgsave快照操作出错时停止写数据到磁盘，这样能保证内存数据和磁盘数据的一致性，但如果不在乎这种一致性，要在bgsave快照操作出错时继续写操作，这里需要配置为no。

3、**rdbcompression：**设置对于存储到磁盘中的快照是否进行压缩，设置为yes时，Redis会采用LZF算法进行压缩；如果不想消耗CPU进行压缩的话，可以设置为no，关闭此功能。

4、**rdbchecksum：**在存储快照以后，还可以让Redis使用CRC64算法来进行数据校验，但这样会消耗一定的性能，如果系统比较在意性能的提升，可以设置为no，关闭此功能。

5、**dbfilename：**Redis持久化数据生成的文件名，默认是dump.rdb，也可以自己配置。

6、**dir：**Redis持久化数据生成文件保存的目录，默认是./即redis的启动目录，也可以自己配置。



#### 4.6 Redis的AOF配置

1、**appendonly**：配置是否开启AOF，yes表示开启，no表示关闭。默认是no。

2、**appendfilename**：AOF保存文件名

3、**appendfsync**：AOF异步持久化策略

​	always：同步持久化，每次发生数据变化会立刻写入到磁盘中。性能较差但数据完整性比较好（慢，安全）
​	everysec：出厂默认推荐，每秒异步记录一次（默认值）
​	no：不即时同步，由操作系统决定何时同步。

4、**no-appendfsync-on-rewrite**：重写时是否可以运用appendsync，默认no，可以保证数据的安全性。

5、**auto-aof-rewrite-percentage**：设置重写的基准百分比

6、**auto-aof-rewrite-min-size**：设置重写的基准值

| ---------- | -------------------- | -------------------- |
| 原理       | 定时全量快照         | 追加写命令日志       |
| 数据安全性 | 低（可能丢大量数据） | 高（最多丢 1 秒）    |
| 文件大小   | 小                   | 大                   |
| 恢复速度   | 极快                 | 慢                   |
| 对性能影响 | 小                   | 较大（IO 密集）      |
| 适用场景   | 冷备、容灾、大数据量 | 核心业务、数据强安全 |

- **核心区别**
  - **RDB：定时快照，全量备份，文件小，恢复快，丢数据多**
  - **AOF：记录每条写命令，实时性高，数据安全，文件大，恢复慢**
- **RDB（Redis Database）**
  - 优点
    - 文件小，备份/传输方便
    - 恢复速度极快
    - 对性能影响小
    - 适合大规模数据恢复
  - 缺点
    - 会丢数据（最后一次快照到宕机之间的数据全丢）
    - fork进程时可能阻塞主进程（极端情况）
  - 触发方式
    - save 60 1000（60 秒内有 1000 次修改就快照）
    - 手动执行 SAVE / BGSAVE
    - 主从同步、关机、重启
- **AOF（Append Only File）**
  - 优点
    - 数据安全性极高
    - 可配置每秒刷盘，最多丢 1 秒数据
    - 日志可阅读、可修复
  - 缺点
    - 文件比 RDB 大很多
    - 恢复速度比 RDB 慢
    - 对磁盘 IO 压力更大
    - 需要定期重写（AOF Rewrite）
  - 同步策略
    - appendfsync always：每次写都刷盘（最安全，最慢）
    - appendfsync everysec：**每秒刷盘（生产推荐）**
    - appendfsync no：由操作系统决定（最快，不安全）



#### 6.2 生产环境怎么选持久化策略

- 标准生产方案：**RDB + AOF 混合使用**

  - RDB：做冷备、快速恢复、灾备
  - AOF：保证数据不丢，最多丢1秒
  - Redis 4.0+ 已经支持混合持久化（最优）

- 推荐配置（直接复制到redis.conf）

  ```
  # ------------- RDB -------------
  save 60 1000
  save 300 100
  save 3600 1
  dbfilename dump.rdb
  dir /var/lib/redis
  
  # ------------- AOF -------------
  appendonly yes
  appendfilename "appendonly.aof"
  appendfsync everysec
  
  # AOF 重写（自动压缩日志）
  auto-aof-rewrite-percentage 100
  auto-aof-rewrite-min-size 64mb
  
  # ------------- 混合持久化（Redis 4.0+）-------------
  aof-use-rdb-preamble yes
  ```

  

#### 6.3 Redis主从复制(Replication)的原理是什么？

- **主从复制**：主写从读，数据同步，实现读写分离与备份。

- **一句话核心：**
  - **主库Master负责写，从库Slave负责读。**
  - **主库数据自动同步到从库，实现读写分离 + 数据备份**

- **作用：**
  - 读写分离：主写、从读
  - 数据备份：一份数据多副本
  - 故障扩容：读性能横向扩展
- **缺点：**
  - **主库挂了👉无法自动切换（必须手动）**
  - **写压力无法分担（只有一个主）**
  - **容量不能水平扩展（所有节点存全量数据）**



#### 6.4 哨兵模式(Sentinel)解决了什么问题？

- **哨兵模式**：监控主从，自动故障切换，解决**高可用**。

- **一句话核心：哨兵 = 自动监控 + 自动故障转移 + 自动主从切换**
- 解决的核心问题：
  - **主库宕机自动恢复**：不用人工介入，哨兵投票选举新主库
  - **集群状态监控**：实时检测 master /slave 是否存活
  - **自动故障转移**：老主挂了 → 自动选新主 → 其他从库指向新主
  - **通知提醒**：故障可发邮件 / 脚本告警
- 不能解决什么
  - **不能解决写压力（还是1主）**
  - **不能解决容量扩容（不能分布式存储）**
  - **不支持多主**



#### 6.5 集群模式(Cluster)解决了什么问题？

- **集群模式**：数据分片存储，多主多从，解决**分布式、扩容、高并发**。

- **一句话核心：Redis 集群 = 分布式 + 水平扩容 + 多主多从 + 高并发 + 海量存储**
- **集群 = 高并发 + 分布式 + 海量数据 + 多主多从**
- 解决的核心问题：
  - **数据分片（分布式存储）：**16384个槽slot，数据分散存在不同主节点
  - **多主架构：**多个主库同时支持写请求
  - **高可用：**自带主从+故障自动转移
  - **横向扩展：**加机器就能提高性能
