## 八、Docker Compose

```
Docker Compose 是 Docker 官方提供的容器编排工具，用于通过 YAML 文件（ docker-compose.yml ） 定义和运行多容器应用。它简化了复杂应用的部署流程，支持一键启动、停止和管理多
个关联容器，适用于开发、测试和轻量级生产环境。
```

### 1. 解决什么问题

- 多容器依赖：如web服务+数据库+缓存redis需要同时运行
- 配置复制：手动执行多个docker run 命令易出错且难以维护
- 环境一致性：确保开发、测试、生产环境使用相同的配置

### 2. 核心功能

- 定义服务：再YAML文件中声明容器（如web、db）
- 一键部署：通过docker-compose up 启动所有容器
- 依赖管理：自动处理容器启动顺序（如数据库先启动，web服务后启动）
- 网络隔离：默认创建独立网络，容器间通过服务名互相访问（如db代替IP）
- 数据持久化：通过volumes挂载宿主机目录或卷

### 3. 基本命令

| 命令                         | 作用                            |
| ---------------------------- | ------------------------------- |
| docker-compose up            | 启动所有服务（前台运行          |
| docker-compose up -d         | 后台运行（推荐                  |
| docker-compose down          | 停止并删除容器、网络 / 停止服务 |
| docker-compose ps            | 查看运行中的容器                |
| docker-compose logs -f       | 查看容器日志                    |
| docker-compose build         | 构建镜像（如果定义了build）     |
| docker-compose up -d --build | 重建镜像（修改配置后）          |
| docker-compose exec xxx bash | 进入容器                        |

### 4. 实战案例

#### **4.1 场景描述**

- 部署一个WordPress博客系统，包含：
  - Web服务：WordPress容器（基于wordpress：latest镜像）
  - 数据库：MySQL 容器
- 需求：
  - 数据持久化（数据库和wordpress上传文件）
  - 容器间通过服务名通讯（wordpress访问db）

#### **4.2 项目结构**

```
wordpress-compose/
├── docker-compose.yml # 配置文件
└── data/ # 持久化数据目录（可选）
    ├── mysql/ # MySQL 数据存储
    └── wordpress/ # WordPress 上传文件
```

#### **4.3 编写docker-compose.yml文件**

```yaml
services:
    db:
        image: mysql:8.0 	# 使用官方 MySQL 镜像
        container_name: mysql_db 	# 自定义容器名
        restart: always 	# 自动重启策略
        environment:
            MYSQL_ROOT_PASSWORD: root123 	# MySQL root 密码
            MYSQL_DATABASE: wordpress 	# 预创建数据库
            MYSQL_USER: wordpress 	# 数据库用户
            MYSQL_PASSWORD: wordpress123 	# 用户密码
        volumes:
        	- ./data/mysql:/var/lib/mysql 	# 持久化数据库数据
        networks:
        	- wp-net 	# 加入自定义网络
    wordpress:
        image: wordpress:latest 	# 使用官方 WordPress 镜像
        container_name: wordpress_app
        restart: always
        ports:
        - "8080:80" 	# 宿主机 8080 映射到容器 80
        environment:
            WORDPRESS_DB_HOST: db 	# 连接 MySQL 服务（通过服务名 db）
            WORDPRESS_DB_USER: wordpress
            WORDPRESS_DB_PASSWORD: wordpress123
            WORDPRESS_DB_NAME: wordpress
        volumes:
        	- ./data/wordpress:/var/www/html/wp-content # 持久化上传文件
        depends_on: 	# 依赖 db 服务
        	- db
        networks:
        	- wp-net
    
networks:
    wp-net: 	# 定义自定义网络
    	driver: bridge
```

#### **4.4 启动服务**

```bash
# 1.进入项目目录
cd wordpress-compose

# 2.启动服务（后台运行）
docker compose up -d

# 3.验证容器状态
docker-compose ps
```

- **访问** **WordPress**：浏览器打开 http://localhost:8080 ，按提示完成安装

## 十、Docker Network

允许容器之间、容器与宿主机、容器与外部网络之间进行通信。

通过虚拟网络技术隔离或互联容器，提供灵活的网络配置选项，适用于开发、测试和生产环境。

#### Docker Network类型

| 网络类型 | 作用                              | 适用场景                           | 示例                                              |
| -------- | --------------------------------- | ---------------------------------- | ------------------------------------------------- |
| bridge   | 默认网络，容器通过NAT访问外部网络 | 单主机开发、测试                   | docker network create  my-bridge                  |
| host     | 容器直接使用宿主机网络，无隔离    | 需要直接访问宿主机资源（如数据库） | --network host                                    |
| overlay  | 跨主机网络（Swarm/K8s集群）       | 分布式应用、微服务                 | docker network create --driver overlay my-overlay |
| none     | 完全隔离，容器无网络访问          | 安全隔离测试                       | --network none                                    |

```
# 示例命令
# bash 1.创建自定义 bridge 网络
docker network create my-net

# 2.启动容器并加入网络
docker run -d --name web --network my-net -p 80:80 nginx

# 3.验证网络
docker network inspect my-net

# 4.测试容器间通信
docker exec -it web ping another-container
```

#### Bridge 网络

- 特点

  - 容器通过虚拟网络互联
  - 每个容器分配独立IP
  - 支持端口映射 -p

- 示例

  ```
  # bash下创建自定义bridge网络
  docker network create my-bridge
  
  # 启动容器并加入网络
  docker run -d --name web --network my-bridge -p 80:80 nginx
  ```

#### Host网

- 特点

  - 容器直接使用宿主机网络栈（无NAT转换）
  - 性能最高，但完全无隔离

- 示例

  ```
  bash # 访问方式：直接通过宿主机IP和端口访问
  
  docker run -d --name my-app --network host nginx
  ```

#### Overlay网络

- 特定

  - 跨主机网络，用于Docker Swarm 或 Kubernetes
  - 通过VXLAN隧道实现容器间通信

- 示例Swarm集群

  ```
  # bash
  # 初始化Swarm集群
  docker swarm init
  
  # 创建overlay网络
  docker network create --driver overlay my-overlay
  
  # 启动服务并加入网络
  docker service create --name web --network my-overlay -p 80:80 nginx
  
  ```

#### None网络

- 特定

  - 容器无任何网络接口，仅lo回环接口
  - 需通过docker exec 手动交互

- 示例

  ```
  # bash
  docker run -d --name isolated --network none alpine tail -f /dev/null
  
  # alpine：使用轻量级的 Alpine Linux 基础镜像
  # tail -f /dev/null：容器启动后执行的命令，作用是让容器持续运行不退出（Alpine 无前台进程会自动停止，该命令是空阻塞，保持容器存活）
  ```

#### 案例场景

##### 微服务架构

- 场景：多个服务（web、API、database）需要互联但隔离
- 方案
  - 创建独立网络，如frontend-net、backend-net
  - 将web和API加入 frontend-net，database加入backend-net
  - 通过frontend-net访问backend-net（需路由配置）

##### 多主机集群

- 场景：跨主机部署容器（如Redis集群）
- 方案
  - 使用overlay网络实现容器间通讯
  - 通过Docker Swarm 管理服务发现

##### 安全隔离

- 场景：限制容器访问权限（如仅允许数据库访问API）
- 方案
  - 创建独立网络（db-net、api-net）
  - 通过防火墙规则限制跨网络流量

## 十一、Docker 目录挂载

#### Bind Mount(绑定挂载)

目录挂载机制,允许将宿主机上的目录或文件直接挂载到容器内部的指定路径

```
# linux mkdir 宿主机目录
mkdir - p ~/nginx_html
echo "<h1>Hello from Host via Bind Mount!</h1>" > ~/nginx_html/index.html

# 运行Nginx容器并挂载Bind Mount
docker run -d -name nginx_with_bind -v ~nainx_html:/usr/share/nginx/html nginx
# 将宿主机的~nainx_html目录挂载到容器的/usr/share/nginx/html
```

高级用法

```
# 只读挂载,防止容器修改宿主机文件
docker run -d --name nginx_ro -v ~/nginx.conf:/etc/nginx/conf.d/custom.conf ngix
```

#### Bind Mount 与 Volume 的对比

| 特性     | Bind Mount             | Volume                                    |
| :------- | ---------------------- | ----------------------------------------- |
| 管理方   | 用户                   | Docker                                    |
| 路径     | 宿主机任意路径         | Docker 自动管理(/var/lib/docker/volumes/) |
| 灵活性   | 高(可挂载任意目录)     | 低(需通过Docker命令管理)                  |
| 适合场景 | 开发环境(代码实时同步) | 生成环境(数据持久化)                      |
| 性能     | 依赖宿主机文件系统     | Docker 优化,性能更高                      |

- 与 Volume 的区别
  - Volume 是 Docker 管理的存储空间,不会直接覆盖容器内的文件,而是合并(如有同名,Volume会隐藏它)
  - Bind Mount 是直接替换



#### 如何避免 Bind Mount 清空容器目录

##### 方法1:先复制容器内的文件到宿主机

1. 运行一个临时容器复制文件到宿主机

   ```
   docker run --rm --name temp_nginx nginx \
   cat /usr/share/nginx/html/index.html > ~/backup_index.html
   # --rm 停止就删
   ```

2. 在宿主机创建目录并放入备份文件

   ```
   mkdir ~/safe_nginx_html
   cp ~/backup_index.html ~/safe_nginx_html/
   ```

3. 挂载Bind Mount

   ```
   docker run -d --name nginx_safe_mount \
   -v ~/safe_nginx_html:/usr/share/nginx/html \
   nginx
   ```

   - 这样容器内的文件不会被清空,因为宿主机目录有备份



##### 方法2:使用volume(推荐)

- volume 合并文件,使用绝对路径

  ```
  docker run -d --name nginx_with_volum \ 
  -v nginx_volume:/usr/share/nginx/html \
  nginx
  ```

  

## 十二、Docker 卷映射

Docker Volume 是 Docker 提供的持久化存储机制，用于将容器内的数据存储到宿主机上，实现数据的

持久化和共享。与 Bind Mount 不同，Volume 由 Docker 管理，独立于容器的生命周期，即使容器被删

除，Volume 中的数据仍然保留.

**核心特点**：

**- 持久化存储**：数据不会因容器删除而丢失。

**- 数据共享**：多个容器可以挂载同一个 Volume，实现数据共享。

**- 性能优化**：Volume 的性能优于 Bind Mount，尤其在 Linux 主机上。

**- 跨平台兼容性**：Volume 的存储路径由 Docker 管理，不依赖宿主机的目录结构。



##### 方法1:使用命名Volume(推荐)

1. 创建volume

   ```
   docker volume create nginx_volume
   ```

2. 运行容器并挂载volum

   ``` 
   docker run -d --name nginx_with_volume \
   	-v nginx_volume:/usr/share/nginx/html \
   	nginx
   ```



##### 方法2:使用Bind Mount(开发环境推荐)

1. 准备宿主机目录和文件

   ```
   mkdir -p ~/nginx_html
   echo "<h1>Hello from Host via Bind Mount!</h1>" > ~/nginx_html/index.html
   ```

   

2. 运行容器并挂载Bind Mount

   ```
   docker run -d --name nginx_with_bind \
   	-v ~/nginx_html:/usr/share/nginx/html \
   	nginx
   ```



**Volume** **的工作原理**

- Volume 是 Docker 管理的独立存储空间，默认存储在 /var/lib/docker/volumes/ （Linux）或 Docker 的存储驱动路径下。

- 当挂载 Volume 到容器目录时
  - 如果 **Volume** **是空的**：容器内的文件会**保留**（但可能被 Volume 的“空状态”隐藏，具体取决于文件系统行为）。
  - 如果 **Volume** **非空**：Volume 中的文件会**覆盖容器内的同名文件**，但其他文件保留。

- 与 Bind Mount 的区别
  - Bind Mount 是直接替换容器目录（类似 mount --bind ），宿主机目录为空则容器目录变空。
  - Volume 是 Docker 管理的存储，行为更“温和”，不会直接清空容器目录。
